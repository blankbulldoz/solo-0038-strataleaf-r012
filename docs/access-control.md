# 身份与授权

StrataLeaf 的授权边界位于库 API 内部。数据库文件本身、`archives.backup` 生成的
备份文件、以及 `replication.export` 产出的提交包都不携带调用方身份；能打开文件或
持有备份的人已经越过该边界。进程内服务的隔离靠身份与授权上下文完成，不靠磁盘权限。

## 身份与三种能力

`Database(path, principal=...)` 绑定句柄的调用身份。同一进程内的其他服务模块通过
`db.as_principal(name)` 取得共享连接、但以另一身份执行的句柄。

身份由 `db.access` 管理，授权是一条当前生效的声明，字段互不推导：

| 参数 | 含义 |
| --- | --- |
| `read=[...]` | 可读取正文的集合；`"*"` 表示全部集合 |
| `write=[...]` | 可写入的集合；`"*"` 表示全部集合 |
| `admin=True` | 管理身份：目录、索引、回收、备份、副本、诊断、身份管理 |

- 只读身份不能写入、不能 patch；可写身份不能读取，除非同时授予 `read`。
- 管理身份隐含全部集合的读写，但不会把身份管理权限传递出去：任何 `admin` 身份都能
  `define`/`update`/`revoke`，但其自身读写范围仍由 `admin` 决定（管理身份始终看到全部）。
- 最后一个管理身份不能被撤销或降级，避免把数据库锁死。
- 新数据库处于 `open` 模式：任何句柄都可读写，用于基线兼容与本地初始化。定义第一个
  身份后立即转为 `enforced`，未带身份的句柄全部被拒绝。`define` 的第一个身份必须由
  匿名本地句柄完成，之后只有管理身份能继续定义。

## 每次调用的授权上下文

`database.access` 之外的所有方法在**执行工作的同一个事务内**解析调用身份并读取其当前
授权。因此授权变更相对读写是线性化的：一个调用按开始时的授权整体执行，`update` 与
`revoke` 不会与它交错。身份名无法被冒用：调用方只能通过 `Database(principal=)` 或
`as_principal(name)` 声明身份，而授权始终从存储中重新解析，句柄本身不缓存权限。

## 跨集合与绕过入口

- **跨集合批次**：`commit` 先校验批次中每个操作的目标集合都可写。任一操作不允许，
  整个批次在写入任何数据前被拒绝，其他集合的正文也不会被写入或泄漏。
- **读路径同样受控**：`get`、历史读、`query`、`aggregates.group`、`transfer.export_lines`
  都要求目标集合可读；未授权的集合一律以 `PermissionDenied`（元数据探测时为
  `NotFound`）拒绝。
- **订阅**：`feed.read` 只交付身份可读的完整提交；提交只要包含任何不可读集合就整体
  不交付，因此不会泄出该提交中其他集合的正文，也不会交付半份提交。消费者记录属于
  注册它的身份，其他身份（非管理）无法读取位置、确认或释放。
- **导出与备份**：`transfer.export_lines` 按集合校验；`archives.backup` 生成整库物理
  副本，需要管理身份。`replication.export/apply` 同为管理身份能力。
- **诊断**：`inspect` 需要管理身份（它报告整库物理清单）；`fingerprint` 只覆盖身份可读
  的集合，并在结果中注明 `scope`，避免把部分指纹当成整库指纹。
- **到期回收**：`retention.sweep` 只删除身份可写的集合中的到期值；不可写集合的到期
  值留给有权的回收者。

## 授权变更期间的游标与保留点

游标和保留点都不是权限凭据，销权不会让它们继续以旧权限生效：

- 游标签名载荷包含签发身份名与授权摘要。续页时若身份名或授权摘要与当前不一致，
  `InvalidCursor` 拒绝并提示重新开始查询；授权收紧后不会用旧授权继续翻页，授权扩大
  后也不会自动获得新集合。由 `open` 模式签发的旧游标在 `enforced` 模式下同样拒绝。
- 读保留点与消费者位置记录其创建身份。撤销身份时同时释放它的保留点与消费者记录，
  使它不再阻止回收；非管理身份只能释放自己名下的保留点。
- 消费确认可以越过不可读的提交：位置本身不泄漏正文，而阻止前进会把回收卡在隐藏
  提交之后。

## 备份与副本的信任边界

- 备份是整库物理副本，包含 `principals` 表，因此需要管理身份才能创建。备份文件等同
  于整库控制权：任何能读到它的人都能得到其全部内容。恢复为新的主库会生成新的
  `database_id` 与新的游标签名密钥，旧库的游标在新库无效；授权配置按备份原样保留，
  所以恢复出的库仍处于 `enforced`，需要原身份句柄访问。恢复为副本保留上游身份并绑定
  该上游。
- 恢复清理保留点与消费者（它们属于旧进程的生命周期）。恢复后的消费方应根据恢复出的
  `floor`/`head` 重新注册。
- 副本提交包的 `sha256` 只检测传输损坏，不做来源认证；`apply` 只接受绑定到配置上游的
  连续范围，且需要副本上的管理身份。因此提交包与承载它的通道必须留在受信任的部署内：
  能向 `apply` 投递包的人即可替换数据库内容。导出校验和不能代替对端身份认证，基线不
  提供网络传输、互相复制或副本提升。
- `open` 模式下备份出的旧式档案没有身份表；恢复到新主库后保持 `open`，应尽快定义身份。
